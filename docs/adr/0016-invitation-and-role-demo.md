## 具体问题

一个人先收下“金华潜水”，邀请朋友时需要看清对方能看到什么、加入后能改什么。样例里的原分享人不等于当前登录成员，不能用封面上的来源姓名授予编辑权限。当前纯前端又无法真正邀请另一台设备，必须把演示双方和真实访问区分开。

## 依据

- 用户已接受一人先使用再邀请朋友，随后授权补齐完整前端 Mock，包含邀请双方与操作边界。
- `lifecycle.js` 的 `canAdd`、`canEdit`、`openSpace`、`generateInvitation`、`openInvitation` 实现本轮流程；修改 / 移除处理也核对角色，不能只靠隐藏按钮。
- Chrome 检查覆盖预览只读、成员维护自己新增记录、邀请过期不能加入及重新生成后继续。
- 当前没有真实账号、服务器授权、发信或跨设备数据连接。

## 候选与当前选择

- 只画邀请成功页：无法评审朋友查看内容与贡献后的区别。
- 所有演示角色都能编辑：简单，但容易掩盖来源与权限归属问题。
- **当前选择：在同一浏览器演示发起人 → 邀请预览 → 朋友只读 / 加入成员，并限制对应操作。** 模拟成员固定为“小禾 · 演示”，不伪造真实朋友已经加入。
- 确认依据：基于本轮前端实现授权，为明确可见内容与操作边界作出的必要选择；最终身份、邀请转发与访问控制仍需后续产品和技术决策。

## 结果与取舍

| 演示身份 | 能看到什么 | 能做什么 |
| --- | --- | --- |
| 发起人：你 | 当前相册全部内容与出处 | 新增、维护 / 移除全部内容、生成演示邀请 |
| 朋友预览 | 当前相册全部内容与出处 | 查看、查找、打开原文；不能新增、更正或移除 |
| 成员：小禾 · 演示 | 当前相册全部内容与出处 | 新增；仅维护 / 移除自己新增的记录 |

操作归属由 `createdBy` 与当前演示操作者判断；`sharer` 等字段仍表达记录来源，原作者、历史分享者与本次操作者不互相替代。成员新增内容进入当前同一本机相册。

邀请页明确提示预览范围和加入后的权限。邀请可生成、预览、加入，也可在“体验场景”中设为过期并重新生成。邀请有效性在加入操作时再次检查。此处过期是明确的演示状态，并未确定生产时限或撤销机制。

没有真实邀请消息、可转发访问私人内容的邀请 URL，也不把本机数据上传到 GitHub。页面外的“体验场景”可切换角色以便验收；它不是生产登录入口。前端操作限制仅用于演示可理解性，不能阻止绕过客户端的访问，不能声称满足生产私人空间权限要求。

## 如何验证 / 何时重看

从发起人生成邀请，核对朋友页明确说明全部可见内容；先预览，确认新增 / 改错 / 移除不可用；加入后新增一条，确认该成员只能维护这条；将邀请设为过期，确认不能继续加入，重新生成后可走通。同一操作在界面和处理逻辑中结果应一致。

引入真实成员或可外传邀请链接前，必须另行决定身份验证、预览是否公开、服务端授权、失效 / 撤销与成员退出后的数据归属，并独立验证。

## 未决问题

免登录预览是否保留、邀请是否可转发、有效期 / 撤销规则、成员移除 / 退出、跨设备同步、权限变更即时生效以及生产个人 / 多共同空间模型仍未确定。
