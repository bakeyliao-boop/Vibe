# ADR-0013：让旧内容浮现带有真实的记忆线索

## 问题与依据

当前换片改变的是封面主位。看到潜水图片时，用户还可能需要“谁分享的、当时什么时候、还有什么相关内容”等线索，才能想起它与自己的关系。

上一轮建议让浮现内容附带真实日期和来源，未来优先展现较久没看过的内容。用户在后续“上面的四点建议我都接受”中确认了该方向；具体排序和卡片信息方案仍需确定。

## 候选与当前建议

- 保持纯随机：简单，但可能只产生视觉变化。
- 自动生成共同喜好或想去结论：原始分享不能证明这些判断。
- **建议：在不增加填写负担的前提下，浮现时带上已有的来源 / 时间线索，再验证是否需要基于长期未查看记录排序。**

“某成员在某日分享”“同一地点还有另外两条”只有对应字段和关联依据存在时才展示。导入时间不能写成原群聊分享时间；多个平台谈及同地点不能自动合并为同作品。

## 结果与取舍

这可能把随机播放变成有上下文的回顾，但需要实际事件数据。当前 `recentFocusedIds` 只规避本次会话最近主焦点，没有长期浏览记录，不能写“很久没看过”或“当年的共同喜好”。

显示多少来源信息、成员间是否共享查看记录、个人未看过和小组未看过如何区分，都需要讨论。不要为实现再发现而默认采集成员的所有浏览行为。

## 如何验证 / 未决问题

比较只看封面与带真实线索的回顾，询问用户是否认出当时的分享、是否打开原文、是否觉得文字干扰松弛感。若已有日期与来源已足够，不必先实现复杂排序。

未确定：长期记录是否必要、浮现优先级、重复分享的记录方式，以及个人查看信息的访问范围。

## 施工前 Mock 的建议范围

先用已存在的分享人、日期及同地点内容数量，展示“这条是谁带来的、还能看到哪些相关分享”。来源不全时保持未知。新内容保存或信息被修改后，相关视图与提示应一致更新。

长期未查看排序仍需记录来源与规则；本次接受方向不代表已有长期历史，也不允许无依据地生成“你们曾经一起去过”。前端流程补齐建议见 [ADR-0014](0014-prebuild-mock-completeness.md)。

## 本轮实现记录（2026-09-12，以下为发布前状态）

本轮在已选内容附近增加轻量线索：原样例显示已有日期与分享来源；本次新增记录显示实际本机收下日期与操作者，并使用“收下”表述，避免冒充原群聊分享时间。地点已确认且存在相关记录时显示“同地点还有 N 条”，点击进入原有稳定的分组全部视图；未知地点不产生虚假关联。

线索由当前相册同一份记录即时计算，更正地点、添加或移除后相关数量与搜索 / 分组同步。Chrome 已检查该联动。继续沿用 ADR-0007 的松弛节奏，编辑或主动查找时暂停自动变化；没有新增长期查看记录，也没有生成共同喜好、共同出行或未查看时长结论。
