# ADR-0009：先验证真实分享能否低成本留存

- 决策状态：提案
- 实施状态：未实现
- 验证状态：有手动准备的真实素材；无自动采集测试结果
- 建档 / 讨论日期：2026-09-12
- 类型：产品 / 数据
- 路线关联：[R2、R3](../../ROADMAP.md)
- 关联：[ADR-0002](0002-content-specimen-and-evidence.md)

## 问题与依据

用户在社交平台看到内容后，若必须另开 App 填标题、地点和类型，保存会成为新的整理工作。当前样例是人工准备的链接和图片，不能证明真实用户分享进来后也能得到相同质量。

此前对食物产品的反馈已经明确了“不愿逐个繁琐录入”的成本敏感性，但新产品的实际保存意愿仍需单独验证。

## 候选与当前建议

- 手动建完整记录：可控但操作重。
- 先做自动读取所有平台收藏 / 群聊：范围和可取得数据未验证。
- **建议：从限定平台的用户主动分享 / 粘贴开始，收到即保留已取得信息，缺失允许稍后补。** 再依据真实输入决定提取、确认和保存方案。

候选记录包含原始分享文本、原链接、平台、实际取得的标题 / 封面、导入时间与操作者。平台内容标识若能可靠取得再保存；不把作者、原群聊分享者与导入者混为一人，也不把导入时间冒充原分享时间。

## 结果与取舍

- 不把完整填写表单作为保存条件，也不伪造缺失字段。
- 先有持久化保存和失败反馈，再评价整理是否足够自动。
- 保留原始分享与标题有助于追溯，但不承诺永久访问原文或恢复正文 / 视频。
- 当前所有样例来自小红书；抖音、微信、微博是产品意向，不属于已实现适配。
- 这条 ADR 没有决定后端、数据库、LLM 或采集服务；需要选择时另立技术 ADR。

## 如何验证

对用户同意用于测试的真实分享，按平台记录：接收成功、可用字段、错误提取、手动补充步骤、保存后能否再次打开。只有原链接无标题 / 封面要单列，不能计为信息完整。再看用户是否会自发继续保存。

## 未决问题

首批支持哪些分享形式？保存到个人还是共同空间怎样默认？重复分享怎样识别并保留来源？哪些字段确实能取得？原文资源的保存边界如何确定？
