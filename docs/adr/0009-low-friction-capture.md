# ADR-0009：先验证真实分享能否低成本留存

- 决策状态：已接受（轻量保存方向与本轮本机 Mock；真实接入待确定）

- 验证状态：Chrome 本机新增、刷新留存、改错联动及异常检查通过；无自动采集或真实用户继续保存证据

## 问题与依据

用户在社交平台看到内容后，若必须另开 App 填标题、地点和类型，保存会成为新的整理工作。当前样例是人工准备的链接和图片，不能证明真实用户分享进来后也能得到相同质量。

此前对食物产品的反馈已经明确了“不愿逐个繁琐录入”的成本敏感性，但新产品的实际保存意愿仍需单独验证。

## 候选与当前建议

- 手动建完整记录：可控但操作重。
- 先做自动读取所有平台收藏 / 群聊：范围和可取得数据未验证。
- **建议：从限定平台的用户主动分享 / 粘贴开始，收到即保留已取得信息，缺失允许稍后补。** 再依据真实输入决定提取、确认和保存方案。

候选记录包含原始分享文本、原链接、平台、实际取得的标题 / 封面、导入时间与操作者。平台内容标识若能可靠取得再保存；不把作者、原群聊分享者与导入者混为一人，也不把导入时间冒充原分享时间。

## 结果与取舍

- 不把完整填写表单作为保存条件，也不伪造缺失字段。
- 先有持久化保存和失败反馈，再评价整理是否足够自动。
- 保留原始分享与标题有助于追溯，但不承诺永久访问原文或恢复正文 / 视频。
- 当前所有样例来自小红书；抖音、微信、微博是产品意向，不属于已实现适配。
- 这条 ADR 没有决定后端、数据库、LLM 或采集服务；需要选择时另立技术 ADR。

## 如何验证

对用户同意用于测试的真实分享，按平台记录：接收成功、可用字段、错误提取、手动补充步骤、保存后能否再次打开。只有原链接无标题 / 封面要单列，不能计为信息完整。再看用户是否会自发继续保存。

## 未决问题

首批支持哪些分享形式？保存到个人还是共同空间怎样默认？重复分享怎样识别并保留来源？哪些字段确实能取得？原文资源的保存边界如何确定？

## 方向确认（2026-09-12）

用户明确表示“上面的四点建议我都接受”，其中包括低成本保存分享内容。本方向转为已接受，实施状态仍为未实现；本次询问施工前完整前端 Mock 还需补哪些，不在该讨论中直接开发真实采集。

下一步的 Mock 建议先展示粘贴 / 接收分享、保存结果、新内容进入相册，以及信息不全、失败、重复输入的继续路径。模拟数据和平台真实解析能力分别记录；详见 [ADR-0014](0014-prebuild-mock-completeness.md)。

## 本轮实现记录（2026-09-12，以下为发布前状态）

用户进一步要求保留现有产品基调进行调整，授权施工前前端流程实现。“收下一条”现可粘贴分享文字或链接、确认预览并保存到当前本机相册；保存成功后，同一记录进入相册、分组及字段查找，刷新后仍保留。未知标题、封面、地点和类型允许待补；内容背面支持更正标题 / 地点 / 类型、移除、撤销，以及复制原链接 / 标题。

保存不联网。小红书已知内容标识匹配预置样例时展示已有资料并明确标注“未联网解析”；陌生链接只使用原链接和用户提供的文字。实际收下时间、当前操作者与原样例分享人分开保存。保守去重、双本机数据池及先写入成功再更新视图的选择见 ADR-0015，不能据此宣称完成平台自动导入。

Chrome 本机检查覆盖：从空相册收下金华潜水示例并刷新留存；更正为苏州 / 美食后分组和搜索同步；移除归零再撤销同一记录；重复输入不新增；模拟失败后重试；只有链接 / 信息不全仍可保存；实际存储写入抛错时旧库和输入保留。尚未完成本轮用户验收、真实 iPhone 系统分享或线上发布核对。
